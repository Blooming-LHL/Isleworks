## 1. 第一版应该做成什么

**一个有 6 位居民的小岛。居民由真实大模型驱动，拥有独立资源、记忆和持续计划，自主决定捕鱼、采集、制造渔网和交易；世界程序严格执行规则，连续运行 30 个模拟日，并允许观察与重放。**

每轮结束后，系统根据整轮事实与最终状态生成 LLM 复盘和有边界的资源参数建议，经过验证、确认后形成下一轮配置，逐步迭代这个小世界。项目采用单进程、模块化架构，明确区分世界执行、居民决策与轮次间评估。

第一版不追求“模拟整个现实经济”，只验证一个核心问题：

> 在资源与时间约束下，有记忆和计划的居民，能否通过储蓄、工具投入、交易与分工，形成值得观察的经济过程？

不预先规定居民必须合作、社会必须繁荣、LLM 必须优于简单规则。停滞、错误投资、交易失败与缺粮都可以是有效实验结果。

### 1.1 对需求的解释与假设

- “自主运行”指启动后由引擎持续推进，不需要用户逐日批准；不是第一版就建设全年运行的云服务。
- “Agentic”必须包含持久目标、跨日计划、执行结果与重规划，不能只是每轮生成一段角色独白。
- “多 Agent 交互”首先通过有实际资源后果的报价与交易实现，不等于先搭建群聊。
- 默认单用户、本地运行；在当前 Isleworks 项目中实现，并以开源发布到 GitHub 为目标。
- 使用一个底层模型服务也可以，但居民的私有状态、记忆和观察必须隔离。
- 本文所有数量、配方、价格机制和失败条件都是待验证的玩具模型假设，不是原书参数或现实定律。
- 第一版的“自我进化”指轮次间的复盘与场景参数校准，不是自动改代码、改经济制度或训练模型。默认自动总结和提案，采纳资源调整前由用户确认；不推定已授权无人值守地改变下一轮世界。

## 2. 从《小岛经济学》中取哪些思想

出版社对原书的介绍涉及资本、储蓄、贸易、风险与借贷等主题；第一版只选择其中可形成最小闭环的部分，不照搬整本书，也不把作者的政策判断写成模拟结论。[Wiley 原书介绍](https://www.wiley.com/en-us/shop/general-finance-investments/how-an-economy-grows-and-why-it-crashes-p-9780470768006)

| 概念 | 在世界里的具体表现 | 可以观察什么 |
| --- | --- | --- |
| 稀缺与机会成本 | 每天劳动时间有限，制造工具会占用捕鱼时间 | 居民如何取舍今天的食物与未来产量 |
| 真实储蓄 | 没有吃掉、没有支付出去的食物库存 | 食物储备是否支持暂时脱离捕鱼 |
| 资本与生产率 | 先投入纤维和劳动制造渔网，再提高捕鱼产出 | 制造成本、使用收益与工具损耗 |
| 交易与分工 | 技能有差异，居民自行报价和成交 | 是否出现相对稳定的专业活动 |
| 不确定性与适应 | 可选择加入一次短期捕鱼冲击 | 是否调整储备、报价与生产计划 |

**有意暂不加入信用。** 先把“现有资源如何分配和转移”做对，再研究“如何对未来资源建立债权”。银行、利息和货币扩张会显著扩大账本与失败处理范围，应留到下一版。

## 3. 范围：少量机制，完整闭环

### 必须有

1. 一个共享小岛、6 个独立居民、每日时间推进。
2. 食物、原材料、渔网三类物品及明确的所有权。
3. 捕鱼、采集、制造、休息和当日交易。
4. 真实 LLM 决策，以及不依赖 LLM 的规则基线。
5. 跨日计划、个人记忆、事件触发重规划。
6. 原子结算、资源校验、日志、日终快照、重放。
7. 一个轻量网页观察器，能看到个体与全岛变化。
8. 轮次结束后的 LLM 总结、资源调整提案、验证结果及可追溯的配置版本。

### 第一版不做

- 银行、贷款、债务、股票、央行、税收与政府。
- 土地产权、工资雇佣、企业组织、跨岛贸易。
- 自由发明配方、自动修改经济规则、执行 Agent 生成的代码。
- 复杂寻路、真实地理、社交媒体、自由群聊、3D 场景。
- 人口出生、家庭结构、复杂生理和情绪系统。
- 模型训练、多智能体强化学习、向量数据库、分布式调度和插件平台。

未来的想象力通过逐步增加经过验证的机制实现，而不是在第一版留下大量空接口。

## 4. 小世界的经济规则

### 4.1 规模与初始条件

| 参数 | 默认建议 |
| --- | --- |
| 居民 | 6 人，全部可使用同一种 LLM，但私有上下文独立 |
| 时间 | 30 日；每天 4 个劳动块，每块抽象为 2 小时 |
| 初始物资 | 每人 2 鱼、0 纤维、0 渔网，全部登记为初始禀赋 |
| 消费需求 | 每人每天消耗 1 鱼；不允许库存不足还照常扣成负数 |
| 信息 | 知道自己的库存与计划、公开规则、昨日市场统计；看不到别人的私有账户和计划 |
| 地理 | 只有小岛与公共市场，地点只用于展示，不引入距离和运输成本 |

“鱼”先抽象为可储存的食物单位，可以理解成鱼干；MVP 暂不模拟腐败。鱼场与植物资源先假设充足，采集受劳动限制，不研究生态枯竭。这些简化必须写在界面和模型说明中。

初始物资与环境丰度属于场景参数；每日消费、技能差异、配方和结算约束属于模型规则。每轮启动时冻结两者的版本和哈希，不能在一轮运行中偷偷改值。原始默认场景始终保留，迭代生成新配置而不覆盖旧配置。

### 4.2 生产与资本

所有居民都能从事所有活动，技能只改变效率，不预先指定终身职业。

| 活动 | 基础规则 |
| --- | --- |
| 徒手捕鱼 | 每劳动块获得 0.5 鱼 |
| 采集纤维 | 每劳动块获得 1 束纤维 |
| 制造渔网 | 消耗 4 束纤维和连续 4 个劳动块，完成后产生一张新网 |
| 使用渔网捕鱼 | 捕鱼产出乘 2，每个捕鱼劳动块消耗 1 点网的耐久 |
| 工具寿命 | 新网耐久 20；归零后记录报废，不允许继续使用 |
| 休息 | 不生产资源，形成闲暇记录 |

为提供分工的可能性，初始设置三类技能禀赋，每类两人：捕鱼效率为每块 0.75 鱼；采集效率为每块 2 束纤维；制网只需连续 2 块。其余技能使用基础值。技能是公开规则，不代表居民必须采用某种职业。

实际捕鱼产出 = 技能基础产出 × 场景捕鱼丰度系数 × 当日冲击系数 × 工具倍率。默认场景丰度为 100%，无冲击为 100%；原有技能与渔网收益不变。第一版只允许能精确换算到 0.001 鱼的组合，拒绝需要隐式浮点舍入的配置。

规则细节：

- 同一劳动块只能执行一个活动。制网一次性预留完整材料和连续时间，不支持半张网或跨日工程。
- 同一天买到的原料可以用于之后的劳动。新网在制造步骤完成后才存在，最早下一劳动块可以使用。
- 每人每个捕鱼块最多使用一张网，多个工具不能叠加倍率。工具以唯一 ID 记录所有者和耐久。
- 市场只交易纤维和全新渔网，暂不处理旧工具折价；买入挂单只能承诺交易前已持有的鱼。
- 每项生产记录投入、劳动与产出来源；“捕获鱼”和“采集纤维”是明确的自然资源获取事件，不是账户转账。

一个人工可行性样例：普通居民起始有 2 鱼，第一天采集 4 纤维并吃 1 鱼；第二天制造一张网并吃完余下 1 鱼；第三天用网捕鱼。这证明投资路径存在，不要求 LLM 必须照做。

### 4.3 交易：先用鱼结算，不额外引入法币

纤维与新网的报价均为“每单位物品多少鱼”。鱼既是消费品，也是本版的交换媒介，因此不存在另一个凭空发薪或增发货币的过程。

这只是为了减少机制数量，不声称真实经济都应使用商品货币。账本字段应叫食物库存和资源储备，不把鱼库存误称为银行存款。

- 每位居民每天最多提交 3 笔限价买卖单；只在当日早间市场有效，结束后全部取消并释放预留资源。
- 所有订单从同一个日初状态生成，先统一收集，不允许先返回模型的居民先交易。
- 引擎先按居民聚合检查所有订单，预留买单最多需要的鱼、卖单承诺的纤维或指定工具；不允许相同资源重复承诺。
- 每种商品买价从高到低、卖价从低到高撮合。买价不低于卖价时，按卖方要价成交；同价用独立、可记录的随机种子打破优先顺序。
- 允许纤维部分成交；渔网按整张和唯一 ID 转移。禁止自己与自己成交。
- 买方获得商品、卖方获得鱼，必须作为一个原子操作一起成功；提交前再次验证可用资源。
- 生产不能使用仍被卖单锁定的材料；市场阶段结束后再统一释放未成交占用。

暂不开放跨日挂单、赊账、未来产量预售和持续合约，直接缩小此前实测发现的重复承诺风险。定价规则是本模型的一项制度选择，必须公开，不能称其为唯一正确的市场机制。

内部使用整数记账：鱼和价格最小单位为 0.001 鱼，纤维按整束、网按整张交易，避免余额校验依赖浮点近似。此处从原方案的 0.01 调整为 0.001，是因为 0.75 鱼的基础产出遇到 50% 冲击会产生 0.375 鱼；所有白名单丰度组合也必须能精确表示，而非悄悄舍入。

### 4.4 消费与失败

每日劳动结束后消费：有足够食物则扣除 1 鱼，否则消费剩余食物并记录缺口。连续 3 日吃不满 1 鱼的居民退出生产与交易，其余库存冻结保留，不从账本中消失；退出状态视为简化模型中的失败，不宣称等价于真实生理死亡。

不自动赠送救济资源。如果所有居民退出，记录岛屿经济失败并提前结束；“世界崩溃”本身是可查看的实验结果。

## 5. Agentic 行为：不能只靠每轮提示词

### 5.1 每个居民至少保留四类状态

| 状态 | 示例 | 谁负责维护 |
| --- | --- | --- |
| 客观事实 | 现有食物、工具、上日成交与工作结果 | 引擎 |
| 私有目标 | 维持储备、获得工具、减少生存劳动 | 居民的结构化目标与偏好 |
| 持续计划 | 未来 3 天的生产安排与条件式交易意图 | LLM 提案，引擎保存并推进 |
| 经验记忆 | 上次报价未成交、预期产量与实际产量不同 | 引擎记录事实，LLM 可更新简短判断 |

给居民不同的安全储备偏好和风险倾向，但不能通过人格文案直接命令“你必须合作”或“你必须证明投资更好”。

### 5.2 规划不是一句自然语言愿望

计划需要包含：目标、有效期限、每天的劳动块安排、交易商品与数量上限、报价、依赖条件、失败条件、当前执行进度与替换原因。

例如，居民可以提出“先积累食物、买纤维、再做网”。但只有实际买到材料、时间足够时，制造才可执行；“已计划买到”不等于库存已增加。

计划执行器每天从已保存计划中生成当天动作，再用真实状态验证；不是每天假装第一次见到这个世界。跨日复用计划时，交易价格与数量意图必须重新检查预算，不能复用昨天的资源锁。

### 5.3 什么时候调用大模型

- 首日建立目标与 3 日计划。
- 计划到期或完成。
- 严重缺粮、关键工具失效、关键交易失败，或实际生产显著偏离预期。
- 已公布的外部冲击到来，需要改变计划。

同一天多个触发条件合并处理，每位居民每天最多一次规划决策。其余时间由执行器继续运行现有计划，不为每个劳动块调用模型。

输入只提供该居民的允许观察、当前计划、近期重要事实和可执行动作定义。输出必须是结构化计划与一两句决策摘要；摘要不是事实证据，也不要求输出完整推理过程。

模型无权修改余额、生成物品、读取别人的私有记忆、调用互联网或执行代码。它只能通过本世界的有限动作接口提案。

### 5.4 多主体交互发生在哪里

六个居民分别决定想买什么、愿付多少、卖什么、如何安排劳动，市场把这些相互竞争的意图转化为真实资源转移。失败的交易和新的公开价格再影响下一次计划。

这已经构成有经济后果的多 Agent 交互，不需要第一版先实现自由聊天。面对面谈判、互信、合伙与信贷，可在交易和合约底层稳定后逐项增加。

## 6. 一天如何推进

| 阶段 | 工作 | 关键约束 |
| --- | --- | --- |
| 日初 | 读取上一日已提交快照，应用已登记的冲击，生成个人观察 | 每人看到的都是同一时间截面的允许信息 |
| 规划 | 并发请求需要重规划的居民，其余沿用计划 | 模型不能在调用期间修改世界 |
| 市场 | 收集当日订单、聚合预留、统一撮合、原子结算、释放锁 | 不按模型返回速度分配交易机会 |
| 劳动 | 按 4 个劳动块验证并执行生产、制造或休息 | 原料、工具与时间均由引擎检查 |
| 日终 | 消费、更新缺粮状态、检查资源账、保存事件与快照 | 校验和持久化成功后，才发布新世界状态 |

同一日各主体的生产不能相互暗中读取中间私有状态；本版只有日初市场，生产中的资源不跨主体转移。不同主体的渔网制造也不竞争共享材料，因此无需复杂并发写入。

用户可以暂停、单步或改变播放速度，但不需要介入每次决策。改变播放速度只影响展示，不改变模拟规则。

## 7. 世界引擎先满足哪些约束

此前对 EconSimulacra 固定提交 `aa1302ed` 的实测显示：自带测试通过，不等于通用结算边界已经兜住任意主体。本版将这些约束作为基础验收，而不是后期优化。

1. 可用量 = 已有库存 - 已预留量，不得为负。
2. 卖单、制造和消费不能重复使用同一物品；工具必须有且仅有一个所有者。
3. 一笔交易两侧同时提交或同时失败；同一个订单与操作 ID 不能被重复执行。
4. 每日鱼库存变化必须能分解为初始量、捕获、消费、交易流入与流出；汇总全岛时交易净变化为零。
5. 纤维变化对应采集与制网消耗；工具变化对应制造、转移与报废；不能把生产转化误判为所有物品数量都应不变。
6. 任何模型异常、非法字段、超时或重复返回，都不能绕过这些约束。
7. 发生结算异常时，不发布部分新状态；日志与已提交日终快照足以定位失败并恢复。

原审计报告仅针对上述提交；不把当时发现直接外推为上游所有后续版本都有同样问题。若未来复用上游代码，应重新核对版本与许可。

## 8. 故障、成本、存档与重放

### 8.1 有边界的自主运行

- 配置每次运行的请求次数、输入输出 token 上限、超时和最大重试次数。默认最多 180 次模型请求尝试，重试也计入预算。
- 正常情况下 6 人每 3 日规划一次，30 日约 60 次决策；事件触发会增加调用，不承诺固定费用。
- 不固定某家付费模型或价格；先用短程真实模型试跑测得 token 和耗时，再由用户确认预算。
- 单次无效输出最多额外重试一次；仍无效时继续执行可用的旧计划，否则当天休息，并明确记录 degraded 状态。
- 服务连续失败或预算耗尽时，保存已提交状态并暂停，不能偷偷把所有 LLM 换成规则主体后仍标为“全自主智能”。
- 轮次复盘使用单独的预算，默认最多 2 次请求尝试（包括重试）；参数验证实验也有独立预算。界面同时展示分项和总用量，不能通过拆预算绕过用户设置的总上限。复盘失败不使已经完成的经济模拟变成失败。
- 主轮默认请求上限为居民决策 180 次加复盘 2 次，共 182 次；启动前同时检查用户的总 token/费用上限并预留复盘额度。若用户上限更低，必须同步缩减决策额度或暂停确认，不能运行完后再额外突破预算。

### 8.2 最小持久化

推荐 SQLite 保存运行配置、提交的世界快照、资源事件、计划版本以及模型请求与响应记录；只有引擎可以写事实状态。模型密钥只从运行环境获取，不写入配置、日志或仓库。

另行保存轮次总结、指标版本、提案、验证实验、确认记录和配置父子关系。运行归档不可变；复盘可以生成新版本，但不能覆盖原始事件或修改过去的最终状态。

每一日先在草稿状态中执行，资源账通过后，将该日事件和新快照在一个事务内提交，再更新观察器。调用模型的记录单独持久化，不把数据库事务跨越整个网络等待过程。

第一版只承诺从最后一个完整日恢复：未提交的日内世界变化丢弃，已记录响应可复用。若请求是否成功无法确认，标记为不确定并暂停确认，而不是无限重试或宣称完全“恰好一次”。

### 8.3 两种不同的重放

- **事实回放**：读取已提交事件和快照，在界面重放，不调用模型。
- **动作重演**：从初始条件、固定随机事件与已记录动作重新执行引擎，比较状态哈希。

相同种子不保证真实 LLM 每次回答一致；要复现一次经济运行，应重用当时的动作记录，而不是重新询问模型。

## 9. 用户第一眼能看到什么

只做一个轻量观察页面，不做完整经营游戏。

| 区域 | 最小内容 |
| --- | --- |
| 小岛总览 | 6 个居民，今天主要活动、渔网与缺粮状态；不需要寻路动画 |
| 居民面板 | 库存、技能、当前目标、计划进度、最近行动结果与简短决策摘要 |
| 公共市场 | 当前报价、实际成交价、成交量与未成交原因 |
| 全岛图表 | 食物库存、每日捕获与消费、渔网数量、劳动与闲暇、缺粮记录 |
| 事件流 | 捕获、制造、交易、报废、计划调整、异常与恢复 |
| 控制栏 | 开始、暂停、单日推进、回放已完成运行 |
| 轮次复盘 | 最终结果、关键转折、LLM 判断所引用的证据和不确定性 |
| 迭代面板 | 原配置与候选配置差异、验证状态、预算、采纳/拒绝与回退入口 |

上帝视角的观察器可以查看所有居民，但这些数据不能自动进入任一居民的模型上下文。没有交易的日子显示“无成交”，不能把上一笔价格伪装成当日市场价。

暂不输出 GDP、通胀或金融健康分等容易误导的复合指标。分别显示物资存量与生产消费流量，不把食物库存直接当作总财富。

## 10. 当前项目的技术方向

在当前 Isleworks 仓库内，用 **Python 的小型确定性引擎 + 可替换决策函数 + SQLite + 轻量网页观察器** 完成第一版，不再把迁移到另一个仓库作为前置步骤。

不直接 fork EconSimulacra 作为核心账本，也不一次拼接多个 Agent 框架。先写清本项目的有限规则及约束，避免一开始继承大量不需要的社交和研究依赖。

只保留必要边界：世界与配方、市场结算、居民计划与决策、运行记录、观察页面。同一份世界执行接口接受规则决策或 LLM 决策；测试替身也用这条路径。

Mesa 可以在之后需要空间管理或批量实验时再评估。其模型、分析和可视化本就分层，但这不替代本项目对交易与计划的定义。[Mesa 官方概览](https://mesa.readthedocs.io/stable/overview.html)

本次不锁定前端框架、模型厂商或具体版本，也不设计通用插件系统。实现时再锁定经过试跑的依赖与模型配置，记录在 lock 文件和运行元数据中。

### 10.1 模块化单体，不做微服务

第一版在同一 Python 进程内划分模块，通过显式的数据对象和函数调用协作。模块是职责和测试边界，不代表每个模块都要部署服务或引入框架。

| 模块 | 核心职责与输入输出 | 明确禁止 |
| --- | --- | --- |
| `domain` | 定义世界、物品、动作、计划、事件、配置及其版本；验证配置类型与基本范围 | 网络调用、数据库访问、运行调度 |
| `engine` | 推进日内阶段，执行生产消费、退出与工具损耗，生成状态草稿和事实事件 | 调用 LLM、按复盘建议改本轮规则 |
| `engine.ledger` | 唯一的资源变更入口；预留、转移、释放、资源检查及操作去重 | 让市场或居民直接修改库存字典 |
| `market` | 根据订单和可用资源生成撮合、预留与结算提案；价格和优先级规则在此定义 | 自己写余额或持久化；绕过 ledger 完成交易 |
| `agents` | 编译个人可见观察，维护记忆、目标和计划进度；提供规则与 LLM 决策两种策略 | 读取其他主体私有上下文、修改世界、跨轮偷偷继承经验 |
| `llm` | 封装模型请求、结构化输出、超时、重试、预算、请求记录与模型标识 | 自行选择经济动作、直接调用世界写接口 |
| `storage` | SQLite 存取、日终事务、归档、模型调用记录、配置和复盘版本；提供查询 | 解释经济规则、计算成交价、替 LLM 改参数 |
| `analysis` | 从不可变归档计算整轮指标、时序与证据片段，输出可校验的事实包 | 用 LLM 编造数字、直接修改场景 |
| `evolution` | 请求 LLM 复盘、校验建议白名单、生成候选配置与验证计划、记录采纳决策 | 写当前世界、执行生成代码、无限启动实验 |
| `runner` | 组装依赖，管理运行状态、阶段调用、恢复、结束和复盘任务，执行获准验证批次 | 重写生产或撮合逻辑，把调度器变成第二套引擎 |
| `interfaces` | 本地 API、CLI 和网页观察器；读取投影，提交开始/暂停/确认等命令 | 直接执行 SQL 改库存或让前端持有模型密钥 |

`engine.ledger` 第一版是 engine 内的子模块，不是另一个服务。`storage` 负责保存已批准的变更，不另建一套经济账务规则。

`llm` 产生结构化调用结果与调用记录，由 runner 交给 storage 保存，不在每个模型适配器内各写一套 SQLite 逻辑。居民决策与轮次复盘可共用请求网关，但使用不同的上下文、输出 schema、预算标签和权限。

### 10.2 依赖方向与唯一写入口

- `domain` 是底层共享类型，不反向依赖任何业务模块。
- `engine` 使用 `domain`、纯计算的 `market` 与内部 ledger；不能依赖 `agents`、`llm`、网页或 SQLite 的具体实现。
- `agents` 根据 `AgentContext` 生成计划和动作；`AgentContext` 必须是经过过滤的数据，不传递完整世界对象或数据库连接。
- `analysis` 只处理归档数据；`evolution` 使用其事实包、`domain` 配置校验及 `llm`，返回报告、参数提案和验证任务描述。
- `runner` 在最上层调用上述模块；验证任务由 runner 调度，evolution 不能反向调用 runner，以免形成循环依赖。
- `interfaces` 通过 runner 发命令，通过查询接口读数据。只有 engine 的 ledger 能决定资源变更，只有 storage 能提交对应持久化事务。

一次日内执行的边界是：runner 取得个人决策 → engine 检查动作 → market 提出撮合 → ledger 验证并应用到草稿 → engine 的资源检查器核对资源 → runner 将 DayCommit 交给 storage 原子提交 → 发布只读观察。正确性不依赖于轮次分析报告。

### 10.3 关键数据契约

| 数据对象 | 生产方 → 消费方 | 最少字段 |
| --- | --- | --- |
| `ScenarioConfigSnapshot` | 配置校验 → runner/engine | 配置 ID、父版本、参数、规则版本、哈希 |
| `AgentContext` | agents 的观察编译器 → 决策策略 | 居民 ID、允许观察、计划版本、事实记忆、动作定义 |
| `PlanProposal` / `DailyIntent` | 居民策略 → engine | 运行/日期/居民 ID、计划 ID、目标、劳动、报价与依赖条件 |
| `SettlementProposal` | market → ledger | 订单及操作 ID、双方、物品、数量、价格、资源预留引用 |
| `DayCommit` | engine → storage | 前一状态哈希、新状态快照、资源事件、计划推进结果、日期 |
| `RunArchive` / `RunMetrics` | storage/analysis → evolution | 终止类型、配置/模型/代码版本、指标与证据 ID |
| `ResourceProposal` | evolution → 配置校验/确认界面 | 父配置哈希、参数路径、旧值、新值、假设、证据、风险、验证状态 |

跨模块传递不可变快照或受约束的数据对象，不共享可修改的库存引用。数值使用既定整数单位，模型只提供允许字段，不能通过自由文本携带要执行的 Python、SQL 或任意配置路径。

### 10.4 建议目录与测试归属

```text
src/isleworks/
  domain/       # 数据类型、配置、规则版本与基本校验
  engine/       # 阶段、生产消费、ledger、资源不变量
  market/       # 订单、撮合与结算提案
  agents/       # 观察、记忆、计划、规则/LLM 策略
  llm/          # 模型适配、结构化响应、预算与记录
  storage/      # SQLite、归档、快照、版本与查询
  analysis/     # 指标、时序、证据包
  evolution/    # 复盘、资源提案、验证计划与采纳记录
  runner/       # 生命周期、依赖组装与有限实验批次
  interfaces/   # CLI、本地 API 与轻量网页
tests/          # 对应模块单测、跨模块集成、端到端及重放测试
scenarios/      # 原始场景和经过确认的派生配置
```

按需从少量文件起步，不要求一开始创建全部空包。ledger 和 market 的测试不能依赖模型网络；agents 使用假的模型客户端测试契约；evolution 测试证据、白名单与版本逻辑；真实 LLM 端到端测试单列、明确计费，不在普通单元测试中暗中触发。

## 11. 轮次结束后的自我迭代机制

### 11.1 两个反馈环，不能混淆

- **轮内反馈**：居民根据自己的经历调整计划，不改变世界规则。
- **轮间反馈**：观察者根据一轮整体事实复盘，提出下一轮资源配置建议。它可以看全局，但不是居民，也不能干预已完成运行。

第一版实现的是“可追溯的场景校准”，不是已经证明世界越来越接近现实。默认每轮重置居民的库存、记忆和计划，不跨轮继承存活者或私有经验；若将来研究主体代际学习，需要另开实验，避免同时改变环境和主体导致无法比较。

### 11.2 什么时候结束并触发总结

| 运行结果 | 处理方式 |
| --- | --- |
| 完整运行 30 日 | 冻结归档，自动生成指标与 LLM 总结 |
| 所有居民提前退出 | 记录实际终止日，作为有效经济失败自动总结；保留失败样本 |
| 用户暂停、预算耗尽或服务中断 | 保留检查点，不视为完成一轮；恢复并结束后再复盘 |
| 引擎不变量违规、数据损坏 | 生成工程故障报告，禁止把故障解释为资源不足并自动调参 |

总结任务以 `run_id + 指标版本 + 复盘版本` 标识，重试不重复生成候选或启动下一轮。总结失败时，经济运行仍标记已完成，总结任务单独重试；复盘用量与模型版本也要保存。

### 11.3 总结必须基于过程与结果，而不只看终局

先由 analysis 计算可信事实包，再交给 LLM 解释。最小输入包括：

- 本轮配置、初始禀赋、规则版本、模型与提示词版本。
- 初始/最终物资、日序列、退出日期、缺粮缺口和居民活动天数。
- 捕获、消费、制造、损耗、劳动分配、成交与未成交原因。
- 计划达成与修订、非法输出、降级、模型故障、预算与调用用量。
- 关键转折的有限事件片段及证据 ID，不把所有原始日志直接塞给模型。

输出包含：结果概览、关键转折、居民策略差异、失败或停滞的可能原因、需要更多证据的判断、保留现状或资源调整建议。每项具体数值必须引用事实包；“缺少资源导致失败”只能先作为假设，不能仅凭终局相关性写成确定因果。

报告采用结构化字段：可验证的数值结论引用 metric_id 与 evidence_id，展示层从事实包填入数值；解释和假设另列。系统校验引用是否存在、参数旧值是否匹配、结构化断言是否成立。自由文本不是可自动证明的事实，不能因模型写得像解释就标记为已验证。无法匹配的结构化内容退回修正，不将 LLM 文字写成账本事实。报告可提供“没有足够证据调整”的结论。

### 11.4 可调整参数白名单

v0.1 每轮最多生成 1 个候选，且只改 1 个参数，优先保持可解释性。

| 参数 | 默认值 | 建议允许范围与单次变化 | 含义 |
| --- | --- | --- | --- |
| `initial_fish_per_agent` | 2 鱼 | 1–3 鱼，每次 ±0.25 鱼 | 下一轮每人相同的初始食物储备 |
| `fishing_abundance_percent` | 100 | 80、100、120，每次移动一个档位 | 环境捕鱼丰度；技能相对差异和工具倍率不变 |

这些边界是首版建议，不是需要由 LLM 自动寻找的“最优范围”。场景从 2 鱼增加到 2.25 鱼，属于下一轮初始禀赋改变，不是向上一轮免费补发资源；新配置必须记录与父配置的差异。

明确不能自动调整：居民数量、日长、每日消费、连续缺粮退出条件、技能、制网配方与耐久、交易结算、记忆隔离、预算上限、评价标准、冲击制度、模型或提示词。不能添加新物品、新制度、任意配置字段或生成代码。需要改变上述机制时，进入人工设计修订流程。

### 11.5 从建议到下一轮的流程

1. **冻结并检查**：存档完成；资源不变量通过。若运行受模型故障或大范围降级主导，只诊断，不把它用作资源校准依据。
2. **生成提案**：LLM 输出假设、证据、参数旧值/新值、预期作用、反效果与验证要求；也允许不改参数。
3. **确定性校验**：检查白名单、范围、整数精度、单参数限制、父配置哈希与模型版本；不合格不进入试验。
4. **低成本筛查**：生成临时候选，用规则主体对原配置和候选作成对试验。建议先用 3 个种子探索，再用另外 2 个预先登记的种子检查；保持规则、策略和冲击相同。
5. **真实主体验证**：规则筛查只能标记“规则环境已筛查”。需要用户明确批准预算后，至少增加一组成对的真实 LLM 运行，再判断候选对自主居民的影响；只有规则结果时不能声称已改善 LLM 世界。
6. **用户确认**：展示证据、代价、风险、验证等级与参数差异。用户可以采纳、拒绝或保留为未验证实验分支，系统不直接覆盖当前默认配置。
7. **创建下一版本**：采纳后新增配置版本和父子关系，新的 run_id 从该配置启动，重新初始化居民。原始默认配置与所有失败运行保留，可显式回退。

确认时再次校验当前采用版本与提案父配置哈希；如果用户已采用其他配置，旧提案只能重新验证或作为明确的分支保留，不能覆盖新版本。

参数试验不能照抄旧运行的动作当作新配置下的自主反应。动作重演只验证同一配置的引擎正确性；比较新资源条件时，主体必须重新决策。真实 LLM 在同种子下也未必相同，因此成对个案只提供线索，不足以证明统计上的改进。

示例（不是实际运行结论）：如果复盘发现多名居民在制造工具前缺粮，应先排除动作无效、计划错误、成交失败与模型故障，再提出“初始食物从 2 鱼增至 2.25 鱼是否能支持工具投入”的假设。即使试验中退出人数减少，也要同时检查闲暇、工具使用和交易变化，并注明初始禀赋变宽松，而不是宣称经济制度或 Agent 智能已进化。

### 11.6 怎样避免“越调越容易”

迭代目标是在明确假设下获得可运行、仍有稀缺与选择的实验环境，不是无限最大化食物库存、成交量或存活人数。

- 正确性、模型调用健康状况先于经济指标；不能通过调参数掩盖结算错误或 API 故障。
- 同时比较缺粮、活动居民日、劳动/闲暇、工具投入、交易与资源分布，不只看最后一天的存活者。提前崩溃按原定 30 日窗口记录退出影响，不能通过缩短分母伪装改善。
- 增加初始资源或丰度带来的改善，要明确标记为环境更宽松，不能说成 Agent 学会了更好的经济策略。
- 评价口径在试验前固定并版本化，LLM 无权改成功标准；保存全部试验，不只留下最好的一轮。
- 每个候选的比较结果单独陈列；不把改变条件后的不同世界硬画成一条“性能持续提高”的曲线。

### 11.7 状态、成本和递归边界

运行终态和复盘终态分开保存。复盘先经历 `pending → summarized`，然后分支：`no_change` 直接结束；需要修改时进入 `proposed → schema_validated → rule_screened → awaiting_llm_validation → awaiting_approval → accepted / rejected`。等待验证和等待确认都是可持久化的状态，各阶段可单独记录失败并重试。

验证批次必须显式设置最大轮数与总预算，子试验使用 `review_enabled=false`，避免每个验证世界结束后又自动启动更多世界。第一版只自动完成总结、提案和确定性校验；低成本批次及真实 LLM 对照由用户发起，不能在后台无上限消耗资源。

迭代面板显示源运行、证据、配置差异、实验 ID、验证等级、确认人和当前采用版本。自动采纳仅作为后续可选模式讨论，本版不实现未经确认的无人值守改参。

## 12. 如何验收：跑通、可信、有自主性分开看

### 12.1 引擎正确性：硬门槛

- [ ] 余额或库存不足、多笔订单重复预留、重复成交、无材料制网、超时劳动均被拒绝。
- [ ] 部分成交正确释放剩余预留；异常不能造成单边转账或半日已发布状态。
- [ ] 生产、消费与损耗均有来源和去向，全部资源账可以核对。
- [ ] 不同模型响应延迟不改变市场处理顺序；同价优先级能记录与复现。
- [ ] 规则基线在至少 10 个随机种子下完成 30 日，或因记录清楚的全体退出而结束；资源约束零违规。
- [ ] 模拟中断后恢复，与相同已记录动作的不中断重演得到相同已提交状态。

### 12.2 真实 LLM 端到端：发布门槛

- [ ] 至少完成一轮 6 居民、30 日的真实模型运行，保留模型标识、调用记录、费用相关用量和失败情况。
- [ ] 计划确实跨日保存并执行，不是每天重建一个没有历史的角色。
- [ ] 缺材料等依赖失败能被识别，产生可追溯的调整或明确失败，而非虚构已经完成。
- [ ] 原始模型输出合法率、降级次数和有效 LLM 决策覆盖率公开；失败或降级过多的运行不能冒充成功展示。
- [ ] 最终展示至少包含一次真实成交、一次工具制造和一次事件后的计划修订；如没有出现，继续检查行为层，不能手写到结果中。

人工脚本或规则主体可以用于确认路径可行，但必须标注为测试，不能充当真实 LLM 自主行为的证据。

### 12.3 经济现象：观察问题，不是规定答案

- 居民是否愿意放弃部分当期产出，换取未来工具收益？
- 是否形成不同的生产与交易策略，专业化是否稳定？
- 交易未必发生时，原因是偏好、报价、信息、规则缺陷还是模型误解？
- 面对产出下降，谁调整储备或计划，谁没有调整？

不能把“没有经济繁荣”直接当软件 bug，也不能通过提示词强迫出现理想结论。需要分开判断实现错误、模型假设和主体决策。

### 12.4 轮次迭代与模块边界：新增验收

- [ ] 完整结束和经济性提前结束均只触发一次对应版本的复盘；暂停与工程异常不误触发资源采纳。
- [ ] 总结数字可回查到确定性指标和事件；编造证据、超出白名单、多个参数同时改变、过期父配置均被拒绝。
- [ ] 复盘调用失败不丢失世界归档；重试不会重新运行 30 日经济，也不会重复派生候选配置。
- [ ] 参数试验标明规则/真实 LLM 验证等级；子试验不会递归生成更多试验，预算包含所有请求尝试。
- [ ] 未经确认，下一轮仍用原采用配置；确认后生成新版本和新运行，原版可重跑、可回退。
- [ ] 规则主体、LLM 主体、复盘模型和界面均不能直接改库存；引擎与账本测试可完全离线运行。
- [ ] 端到端至少完成“30 日运行 → 有证据的总结 → 合法建议或保留现状”；参数调整功能另需一次验证、确认和派生场景启动的集成测试，不以强迫 LLM 必须提出修改作为通过条件。

## 13. 第一版只保留三类场景与必要对照

1. **基础场景**：上述规则，检查世界是否能持续运转。
2. **无渔网场景**：关闭工具配方，其他条件不变，用于观察资本机制带来的差别。
3. **短期捕鱼冲击**：例如第 15–17 日捕鱼产量乘 0.5，冲击开始才公开；之后恢复。随机环境事件使用独立随机流，避免不同策略消耗随机数后改变冲击条件。

决策对照使用同一个引擎：可投资与交易的简单规则主体；只做当天决定的 LLM；具有持久计划的 LLM。第一轮先跑规则基线与带计划 LLM；有余量后增加即时 LLM 对照，避免把实验矩阵做成首发负担。

对照尽量保持技能、禀赋、规则和环境冲击相同。对 LLM 记录模型配置与输入输出预算；单次展示只证明个案，不能宣称具有统计优势。

原始三类场景是稳定基准，不由轮次迭代覆盖。第 11 节产生的是带父版本的参数变体；比较时不能同时更换居民策略、模型与资源条件。

## 15. 后续每学一个概念，怎样扩展

按“问题 → 明确机制 → 资源与账务约束 → 对照实验 → 文档解释”扩展，而不是学到一个名词就增加一个角色。

| 后续学习主题 | 可能增加的机制 | 必须先补的边界 |
| --- | --- | --- |
| 信用与利息 | 居民之间借出已存在的鱼，到期偿还 | 债权债务配对、履约、违约与不能凭空还款 |
| 企业与工资 | 雇佣、投入产出、利润分配 | 工资由谁支付、产品归谁、破产如何结算 |
| 货币与银行 | 从商品结算过渡到记账货币与银行 | 发行规则、资产负债表、清算与可追踪的信用创造 |
| 生态与外部性 | 有限鱼群与再生、过度捕捞 | 资源状态与公共资源治理规则 |

这些是扩展方向，不是 v0.1 的预留功能清单。第一版只需要证明：居民会规划、会交互，世界会坚持约束，结果可以被观察和检验。
